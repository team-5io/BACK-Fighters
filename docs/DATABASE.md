# DATABASE.md

## 시간대 정책

- 서버 JVM 기본 시간대는 UTC로 사용한다.
- 데이터베이스에 저장하는 날짜·시간의 기준은 `Asia/Seoul (UTC+09:00)`이다.
- 날짜·시간 생성·변환 시 시스템 기본 시간대에 의존하지 않고, `Asia/Seoul` 또는 UTC를 명시적으로 사용한다.
- API 응답은 `Asia/Seoul` 기준의 ISO-8601 오프셋 형식으로 반환한다.
- 생성일·수정일 컬럼을 갖는 JPA Entity의 상속 규칙은 [ARCHITECTURE.md](ARCHITECTURE.md)의 "Domain Model과 JPA Entity" 섹션을 따른다.

## Flyway 마이그레이션

- Flyway는 `out-of-order: true`로 실행한다. 여러 팀원이 병렬로 브랜치 작업을 하다 보면, 나중에 머지되는 마이그레이션의 버전 번호가 이미 적용된 최대 버전보다 낮을 수 있기 때문이다.
- **주의**: out-of-order는 "버전 번호가 뒤섞여 병합되는 상황"은 해결해주지만, "A 마이그레이션이 참조하는 테이블을 B 마이그레이션이 나중 번호로 생성하는" 의존성 순서 역전까지는 막아주지 않는다. 기존 dev/운영 DB는 이미 적용된 이력 덕분에 우연히 통과할 수 있지만, 빈 DB에 처음부터 전체를 실행하면 실패한다.
- 마이그레이션 파일은 `src/main/resources/db/migration/be{담당자번호}/` 경로에 생성한다. 담당자번호는 팀 내부에서 합의해 배정한다.
- 파일명은 `V{담당자번호}.{묶음번호}.{순번}__{설명}.sql` 형식을 사용한다.
- 같은 담당자번호와 묶음번호 안에서는 순번을 `1`부터 `9`까지 사용한다. 순번이 `9`에 도달하면 묶음번호를 증가시키고 순번을 `1`부터 다시 시작한다.
  - 예: `V1.1.1__create_users_table.sql`부터 `V1.1.9__...sql`까지 사용한 다음 파일은 `V1.2.1__...sql`로 생성한다.
- 이미 배포된 마이그레이션 파일은 수정하거나 삭제하지 않는다.
- 신규 마이그레이션은 참조하는 테이블/컬럼이 다른 담당자 폴더의 마이그레이션에서 먼저 생성되는지 반드시 확인한다.
- CI(또는 로컬 검증)로 완전히 빈 스키마에서 전체 마이그레이션이 순서대로 성공하는지 확인하는 것을 권장한다. **담당자별 버전 번호를 계속 쓰는 한 이 검증이 실질적인 유일한 안전장치다** — 번호 방식 자체는 순서 역전을 구조적으로 막아주지 않는다.

### 충돌 발생 시 대응

빈 DB에서 전체 마이그레이션 중 일부가 실패하면 다음 순서로 해결한다.

1. 실패한 마이그레이션의 버전과 SQL 에러(주로 "테이블/컬럼이 존재하지 않음")를 확인한다.
2. 그 마이그레이션이 참조하는 테이블/컬럼을 실제로 생성하는 마이그레이션 파일을 찾는다.
3. 참조하는 쪽의 버전(묶음번호.순번)이 생성하는 쪽보다 낮다면, 참조하는 쪽의 버전을 생성하는 쪽보다 높게 재조정한다.
4. 로컬에서 빈 MySQL(Testcontainers 또는 throwaway 컨테이너)에 재현해 확인 후 다시 push한다.
